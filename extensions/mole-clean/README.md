# Mole 深度清理

给 Jarvis 的清理换一台更深的引擎。打开之后，晃球、`/clean` 与工具箱里的「清理」都改走你自己装好的
[Mole](https://github.com/tw93/mole)（`mo clean`）：浏览器、开发工具、云盘与办公、已卸载应用残留、
设备固件这些 Jarvis 自带的清理不碰的类别，也一并清掉。

它**没有自己的界面**，不出现在工具箱目录里——它是一个服务扩展，实现 Jarvis 开放的 `junkClean.engine`
扩展点。悬浮球、进度、结果页仍是 Jarvis 自己的那一套；扩展只负责跑 `mo`、读它的输出，把数字交回去。

## 它做什么

- **跑 `mo clean`**：不带任何参数，在非交互模式下跑（见「已知边界」第一条）。
- **实时进度**：每 0.5 秒读一次 Mole 的操作日志，「已释放」与「正在删哪一项」跟着 Mole 每删一个文件往上走——
  不必等一整类做完才跳一下。
- **分类结果**：按 Mole 的区段列出每一类清掉了多少、几项、哪几项没删掉（每类最多列 3 条，其余写「另有 N 项」），
  区段名翻成中文（「User essentials」→「用户缓存、日志与废纸篓」）。
- **整次说明**：系统级那一段被跳过、磁盘可用空间的真实变化、按白名单跳过了几项、Mole 自己的统计与明细之和对不上时差在哪。
- **没装 `mo` 时**：引擎卡上给一颗「在终端中安装」，装好之后自动换成 Mole，不用回来再点什么。

## 要哪些授权，为什么

三项，全部是**高风险**档。第一次在 `设置 · 清理` 里打开它时 Jarvis 弹一次授权屏一次问完；
之后可以在 `设置 · 扩展` 里它那块面板上逐项撤销。

| 能力 | 拿来做什么 | 宿主替你拦住的 |
| --- | --- | --- |
| `process.run` | 跑 `mo clean`（清理）与 `mo --version`（引擎卡上的版本号） | 只放行名为 `mo` 的可执行文件、只放行这两组参数，逐项比对；不经 shell |
| `files.read` | 读 `~/Library/Logs/mole/operations.log`，逐项显示正在删什么 | 只这一个文件，只读 |
| `terminal.run` | 没装 `mo` 时，打开终端执行 manifest 里那段「安装 Mole」脚本 | 扩展只能按 id 点名，不能传脚本内容；脚本全文写在 `extension.json` 里，装之前就能读到 |

**`mo` 继承 Jarvis 的全部系统权限，包括完全磁盘访问。** 这是它比你在一个没有完全磁盘访问的终端里跑 `mo clean`
清得更全的原因，也是 `process.run` 是高风险的原因：Jarvis 有权读写的地方，`mo` 也有。授权之前请确认你信任
自己装的那一份 Mole。

撤销 `files.read` 之后照样能清，只是进度退回「每一类做完时跳一下」；撤销 `process.run` 之后引擎卡写明原因，
这一次回落到 Jarvis 清理。扩展自己**不联网、不写任何存储**；安装脚本里的 `curl` 是在你的终端里、你眼前跑的。

## 怎么用

1. 在扩展商店装上「Mole 深度清理」。
2. 打开 `设置 · 清理`，打开「深度清理（Mole）」。第一次打开时批准授权屏上的三项。
3. 引擎卡写着「没有找到 mo 命令」时，点「在终端中安装」：
   - 有 Homebrew：`brew install mole`；
   - 没有：下载 Mole 官方安装脚本，装到 `~/.local/bin`（不要管理员密码）。

   终端里先写出将要执行的命令再跑，跑完停住等回车关闭。Jarvis 同时每 2 秒重查一次（最多 10 分钟），找到即换成 Mole。
4. 之后晃球、`/clean`、工具箱「清理」都走 Mole。关掉开关就回到 Jarvis 清理。

### 设置

| 项 | 默认 | 说明 |
| --- | --- | --- |
| `mo 命令` | `mo` | 填 `mo` 时由 Jarvis 在 Homebrew（`/opt/homebrew/bin`、`/usr/local/bin`）、`~/.local/bin`、`~/bin` 与 Nix 的固定位置里找。也可以填可执行文件的完整路径（`~` 开头也行），文件名必须是 `mo` |

填了路径而那个路径坏了，引擎卡就**报坏**（「填的路径 … 不存在」「… 不是可执行文件」），**不悄悄回落到自动查找**：
你明确指定的那一份被换掉、屏幕上却一切正常，是最难查的一种错。这种情况下也不给「在终端中安装」——
装一个新的救不了写错的路径，该去改设置。

## 它怎么算数

- **两路明细，每一类取大的那个。** 标准输出在每个清理目标做完后打一行小结；操作日志每删一项当场记一行。两边都不完整：
  浏览器 Service Worker、`npm cache clean` 这类用命令清的只在标准输出里，一个目标中途被打断时只有日志记得删掉了多少。
  相加会重复计，取大的那个才是「至少清掉了这么多」。
- **只认一次会话。** 日志里开跑之后出现的第一个 `clean` 会话就是这一次；之前的记录、别的命令（`mo optimize`）的会话都不算。
- **进度估计。** Mole 的区段永远按同一个顺序出现（系统 → 用户缓存 → 应用缓存 → 浏览器 → … → 项目构建产物，共 15 段），
  「到了第几段」就是诚实的进度；不认识的新区段不推进、也不倒退。
- **Mole 自己的总数。** 它的「Tracked cleanup」不计浏览器 Service Worker 等几项，与明细之和差 1 MB 以上时结果页会写一句，
  以明细为准。

## 已知边界

- **系统级那一段一律跳过。** `mo` 在非交互模式下跑：不提示、不卡住、**不要密码**；没有现成的 sudo 会话时，
  需要管理员权限的那一段整段跳过，结果页写明这一点。要清它，在终端里自己跑 `sudo mo clean`。
- **永久删除，不经过废纸篓；Mole 还会清空废纸篓。** Jarvis 的路径校验与「运行中的应用不清」保护只覆盖 Jarvis 自己的清理，
  管不到 `mo`——要留的东西写进 Mole 的白名单 `~/.config/mole/whitelist`。这份白名单 Jarvis 清理也认，两边同一份例外。
- **没有日志就没有逐项明细。** 关掉了 Mole 的操作日志（`MO_NO_OPLOG=1`）、撤销了 `files.read`、或者 Mole 版本早到日志里
  没有 run id 时，只看标准输出：一个目标删上几分钟时进度停在原地，直到那一类做完。
- **日志按时机归类。** 日志行不写自己属于哪一类，只能按「此刻标准输出停在哪一段」归；输出每 100ms 合批送达，
  一段末尾与下一段开头的几项偶尔会被归到相邻的那一段。总数不受影响。
- **同时在终端里也跑 `mo clean`** 时，日志里先开始的那一次会话会被当成这一次，明细可能张冠李戴。
- **取消** 会中断 `mo`（SIGINT）。已经删掉的不会恢复，结果页照样列出来；Mole 来得及收尾时写它自己的说法
  （「Cleanup interrupted」），来不及时写「已取消」。
- **引擎卡上的路径是绝对路径**（`/Users/<你>/.local/bin/mo`）：扩展不知道你的主目录在哪，也不需要知道。
- **`mo --version` 5 秒没回来就不等了**：引擎卡只写路径不写版本，照样可用。
- 结果页里不认识的 Mole 区段原样显示英文名：Mole 新加了区段时照样能清、能看，只是没翻译，等扩展发新版本。
