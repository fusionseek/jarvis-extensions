# Jarvis 开放平台 · 总览

## Overview

Jarvis 的工具箱、全局搜索、速记、设置页与清理都是 Swift 写进 `jarvis-mac` 的**内置能力**，
加一件要走一次 Speckit、改一串 `switch`、发一版应用。开放平台把「加一件事」交给应用之外的人：
开发者在本仓库（`fusionseek/jarvis-extensions`）里写一个**扩展**，合并进主干；用户在 Jarvis 的**扩展商店**
里装上它，它就出现在它声明入驻的那几处——与内置的东西同一套 header、字阶、色板与悬停光，用户分不出哪一处是原生的。

这份文档回答**为什么**与**边界**。怎么做见后面十三篇。

**v2 是一次不兼容的换代**（`jarvis-mac` spec `20261011-193606-extension-domains-service-engines`）：manifest、
registry、线缆协议、SDK 一起升到 2，宿主不读任何 v1 的东西，本机装过的 v1 扩展在新版第一次读清单时整批卸掉。
理由写在 [14](14-host-integration-plan.md)：用户与扩展都还少，一层过渡代码留下的隐患比让几个人重新装一次贵得多。

## Concepts

### 扩展按「域」入驻

Jarvis 的界面与能力分成下面几个域。**一个扩展在 manifest 的 `contributes` 里声明它入驻哪几个域**，没声明的域它碰不到。

| 域 | manifest | 用户看到 | 规则 |
|---|---|---|---|
| **悬浮球** | —（不存在这个键） | — | **扩展什么都不能做**。悬浮球是主入口，手势、动画、状态点、读数都是固定能力。扩展只能**间接**影响它：扩展一个本来就驱动悬浮球的内置能力（例如清理引擎），悬浮球照旧读那个内置能力的通用状态 |
| **工具箱** | `contributes.toolbox` | 工具箱目录里一行；点开是面板里 400×520 的一页 | 与内置工具同一套 header 与交互；面板几何一个字都碰不到 |
| **窗口** | `contributes.window` | Jarvis 工作区窗口里一枚标签 | 同一棵节点树画在窗口里，宽度不受 400 限制；一个扩展至多一枚 |
| **指令** | `contributes.commands` | 全局搜索与速记输入框里的 `/` 指令、全局快捷键 | 应用启动时宿主把内置指令与扩展指令合成一张表；关键词与内置撞了，扩展那条不加载。**受限执行命令**（`process.run` / `terminal.run`）归这个域 |
| **设置** | `contributes.settings` | 设置页「扩展」区段里它那块面板 | 控件由宿主画，扩展只声明类型与约束 |
| **服务** | `contributes.services` | **没有独立界面**，体现在它扩展的那个内置能力里 | 只能插到宿主开放的**扩展点**上（`junkClean.engine` 清理引擎、`project.engine` 项目引擎）；跑在独立的后台会话里；它的设置画在那个内置能力的设置区段里 |
| **Git** | `contributes.git` | Git 设置对应托管服务下它的「关联」区段 | **不是入口**：它决定扩展在 Git 里出现在哪、碰得到哪几个托管服务；Git 操作域的能力（`git.*`）只给入驻了它的扩展 |
| Inbox（通道） | `inbox` | Inbox 里一条消息、系统横幅 | 不是域：任何域里的代码都可以用它交结果 |

`contributes` 至少要有工具箱、窗口、指令、服务之一——只有设置的扩展没有入口，是一个永远不会跑的扩展。

### 为什么分域

v1 只有一种扩展：工具箱里一行、点开一页。可很多值得做的事没有页面——给内置清理换一台更深的引擎、
给全局搜索加一条 `/http`、给一个已经很好的内置能力接上第三方的更优实现。把它们硬塞进工具箱，
工具箱里就多一行点进去什么都没有的东西；不给它们位置，这些能力只能等 Jarvis 自己写。

分域之后，扩展说"我入驻哪几处"，宿主替它在那几处画好入口；**哪几处可以入驻是宿主定的**，不是扩展发明的——
悬浮球不开放，因为它是用户每天按一百次的东西，任何一个扩展能改它的手势或动画，Jarvis 就不再是同一个产品。

### 服务扩展：给内置能力换实现

服务域是 v2 新加的那一种。它解决的问题是：**内置能力做得对、做得安全，但不一定是最强的那一个**。
例如 Jarvis 清理只清不需要管理员权限的用户级目录、每一项删除前都过自己的安全检查；而 Mole（`mo clean`）
覆盖的类别多得多。把 Mole 写进主程序，Jarvis 就背上了一个第三方命令行工具的全部细节；做成服务扩展，
主程序只认识「清理引擎」这个扩展点，Mole 的调用、输出解析、安装脚本都在扩展里
（[`extensions/mole-clean`](../extensions/mole-clean)）。

```text
悬浮球 / /clean / 工具箱「清理」 ──▶ JunkCleanCoordinator ──▶ 选中的引擎
                                                          ├─ Jarvis 清理（内置）
                                                          └─ junkClean.engine 服务（扩展的后台会话）
```

悬浮球读的仍是协调器那份通用状态：它不知道、也不需要知道这一次是哪一个引擎在删。

## 为什么是这条运行时路线

扩展的代码**跑在宿主进程里的 JavaScriptCore**（macOS 自带的系统框架，零第三方依赖），
**界面是一棵声明式节点树，由宿主用 SwiftUI 画出来**。扩展不画像素：它说「这里一段、一行输入框、
一颗主按钮」，宿主用内置工具用的那几份 tokens 与那几个视图把它画出来。

这是在四条路里挑出来的一条，另外三条各有一处走不通：

| 路线 | 走不通的地方 |
| --- | --- |
| **Swift 源码编进宿主** | 与"从 git 仓库罗列、点一下装上"直接冲突：装一个扩展等于发一版 Jarvis。它保留为内置能力的做法 |
| **动态加载原生 `.bundle`** | 把陌生的原生代码 `dlopen` 进一个常驻、拿着屏幕录制与完全磁盘访问的进程，签名、公证、ABI 冻结每一样都是独立工程；一旦崩溃带走的是整个 Jarvis |
| **WKWebView 里跑 HTML** | 与「用 SF Symbols、不复制 Web 组件外观」「全应用唯一字体出口 `Font.jarvis`」冲突 |
| **JS 逻辑 + 声明式原生 UI（选定）** | 代价是组件目录是**封闭**的：扩展只能用宿主提供的 31 种节点。这是"风格统一、交互一致"的代价，不是缺陷 |

服务扩展同样跑在 JavaScriptCore 里：它要做的是"调一个外部命令、读它的输出、交回一份报告"，
这些全部经宿主的受限执行能力完成，扩展自己没有进程、没有文件系统。

## 平台的六条原则

1. **面板是容器，内容才是模式。** 扩展只是又一块内容。窗口几何、收放动画、15 秒倒计时、header 骨架
   在扩展页面上与内置工具完全相同；扩展一个字都碰不到它们。
2. **同一条轮廓上只允许存在一条边。** 扩展不能自带底色、圆角、描边或投影；它能选的只有语义（`tint` / `variant` / `style`）。
3. **可点的东西自己会亮。** 每一颗可交互节点由宿主自动挂悬停光；失效的控件一律不亮。
4. **没有点头就没有能力。** 能力闸门在宿主侧、每一次调用都过；系统权限（屏幕录制、完全磁盘访问）是 Jarvis 的，
   扩展只能借用。受限执行的每一个对象（可执行文件与参数、文件路径、终端脚本）都要在 manifest 里逐字写出来。
5. **悬浮球不开放。** 扩展只能经由一个本来就驱动悬浮球的内置能力间接影响它。
6. **结构化数据只有一个库。** 扩展的安装记录、授权、偏好、存储全部进 `jarvis.sqlite3`；机密进钥匙串；扩展自己没有文件系统。

## Usage

- 用户：工具箱末尾那枚虚化的加号 → 扩展商店 → 安装；装完的回执按域说它去了哪儿（工具箱一行、`/` 指令、
  设置 · 清理 里的开关……）。
- 开发者：从 [12 · 开发手册](12-developer-guide.md) 开始；manifest 逐字段见 [03](03-manifest.md)。
- 审核者：[13 · 审核清单](13-review-checklist.md)。

## 不做什么

- **不做第二种运行时。** 没有 Swift 扩展、没有 WebView 扩展。
- **不做任意命令执行。** `process.run` 只放行 manifest 里声明过的可执行文件与参数组合；`terminal.run` 只执行
  manifest 里逐字写着的脚本；没有 shell、没有通配。
- **不做应用内商店的账号、评分、付费。** 扩展商店就是这个仓库的一份快照，上架靠 PR 审核。
- **不做自定义像素。** 想要一种新控件，正确的路是给组件目录提 PR。
- **不做开发者模式**（本地目录加载、热重载）——这一版宿主还没有，见 [12](12-developer-guide.md)。
- **不做快捷环里的扩展球、Inbox 卡片上的动作按钮。**
- **不兼容 v1。** 宿主不读 v1 manifest、registry、线缆与 SDK 1.x 的产物。

## 术语

| 词 | 含义 |
| --- | --- |
| 宿主 | `jarvis-mac` 里承载扩展的那一层：运行时、渲染器、能力闸门、扩展商店、安装记录、扩展点 |
| 扩展 | `extensions/<id>/` 一个目录：`extension.json` + `dist/extension.js` + 源码与 README |
| 域 | 扩展可以入驻的一处：工具箱、窗口、指令、设置、服务、Git（悬浮球不是） |
| 扩展点 | 宿主开放给服务扩展的一个契约（`junkClean.engine`、`project.engine`）：方法、参数、返回值、设置画在哪 |
| 前台会话 | 有界面的那一个扩展运行时（全应用至多一个）：工具箱页面、原地弹窗、窗口标签三面 |
| 后台会话 | 没有界面的运行时（每个扩展至多一个）：服务调用与静默命令 |
| 快照 | 宿主从 GitHub 拉下来、解开放在本机缓存目录里的一份仓库归档 |
| 能力 | `jarvis.*` 上一个需要用户点头的命名空间（`clipboard.read` …）；隐式能力不需要点头 |

```text
├── sdk/                       @fusionseek/jarvis-extension-sdk 2.x
├── templates/hello-extension/ 脚手架
├── scripts/                   校验与生成 registry
└── extensions/<id>/           每个扩展一个目录
```

## Gotchas

- 「服务扩展」不是「后台常驻」：它没有常驻进程，只在宿主调它时才起后台会话，空闲一分钟就收掉。
- 入驻工具箱与入驻窗口是两件事：只入驻窗口的扩展不在工具箱目录里，从全局搜索、`/` 指令或页面按钮打开。
- 改 `id` 等于换一个扩展：安装记录、授权、偏好、存储全部按 `id` 隔离。
